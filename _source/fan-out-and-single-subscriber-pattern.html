Pola Arsitektur Fan-Out vs Single Subscriber di Cloud Computing

Dalam desain sistem terdistribusi modern berbasis Event-Driven Architecture (EDA), pemilihan mekanisme pengiriman pesan antar-layanan sering kali menentukan skalabilitas, fault isolation, dan kemudahan evolusi sistem di masa depan.

📌 Definisi Singkat Arsitektur

Fan-Out Pattern: Pola one-to-many di mana sebuah event message dikirimkan ke satu Topic, lalu didistribusikan secara independen dan paralel ke banyak antrean/subscriber berbeda tanpa saling memblokir.

Single Subscriber Pattern: Pola di mana sebuah antrean atau topic hanya memiliki satu entitas downstream yang memproses pesan (point-to-point / worker queue), sering kali dimanfaatkan untuk load buffering atau perataan beban (compaction/rate limiting).

1. Arsitektur Fan-Out (One-to-Many Broadcasting)

Ketika sebuah tindakan bisnis terjadi (misalnya pengguna melakukan checkout barang atau memutar lagu), banyak domain bisnis berbeda yang berkepentingan terhadap kejadian tersebut tanpa perlu sang produsen tahu siapa saja penerimanya.

[ Publisher / Producer ] │ ▼ (1 Event: e.g. "OrderPlaced" / "TrackPlayed") ┌───────────────┐ │ Pub/Sub Topic │ (GCP Cloud Pub/Sub Topic / AWS SNS Topic) └───────┬───────┘ │ ├──► (Subscription A / SQS 1) ──► [ Inventory / Stock Service ] ├──► (Subscription B / SQS 2) ──► [ Billing & Royalty Accounting ] ├──► (Subscription C / SQS 3) ──► [ Real-time ML Recommendation Engine ] └──► (Subscription D / SQS 4) ──► [ Notification Service (Email/SMS) ]

Kasus Nyata di Industri (Real-World Case):

  • Spotify (Streaming Playback Pipeline):
    Ketika pengguna menekan tombol Play, layanan pemutar mengirim event TrackPlayed ke Google Cloud Pub/Sub. Dari satu event ini, arsitektur fan-out menduplikasi pesan ke tiga kanal independen:
    1. Subscription 1 (Streaming ML / Apache Beam): Menghitung riwayat rekomendasi pengguna (fitur Discover Weekly).
    2. Subscription 2 (Royalty Accounting): Menghitung hak cipta dan royalti artis per putaran lagu.
    3. Subscription 3 (Social Feed): Memperbarui status aktivitas ke teman di aplikasi.
  • Shopify (Merchant Event Distribution):
    Shopify memanfaatkan Google Cloud Pub/Sub untuk mendistribusikan jutaan webhook event (seperti orders/create). Melalui Fan-Out, event order dialirkan serentak ke sistem inventaris toko, kalkulasi analitik merchant, dan fraud detection.

2. Pola Single Subscriber (Kapan dan Mengapa Digunakan?)

Ada anggapan keliru bahwa jika hanya ada satu pemroses di hilir, produsen cukup langsung memanggil API HTTP konsumen secara langsung (Point-to-Point). Namun dalam standar rekayasa cloud (SOP), pola Single Subscriber dengan Message Queue justru sangat krusial.

[ Producer Service ] ──► [ Message Topic / Queue ] ──► [ Single Subscriber Worker ] │ (Buffer & Shock Absorber)

Mengapa Menggunakan Buffer Topic/Queue untuk 1 Subscriber?

  1. Shock Absorber / Rate Limiting (Peredam Lonjakan Beban):
    Jika 10.000 pesanan masuk dalam 1 detik (misal flash sale), database konsumen hilir akan mati jika ditembak HTTP langsung. Dengan meletakkan antrean di depan Single Subscriber, worker dapat mengambil (pull) pesan dengan kecepatan yang mampu ditangani database (misal 50 pesan/detik) tanpa ada satu pun pesanan yang hilang.
  2. Fault Isolation & Zero Downtime Deployment:
    Jika layanan subscriber harus restart, mengalami crash, atau sedang di-deploy, pesan tetap aman tersimpan di storage Pub/Sub / SQS (hingga 7–14 hari). Begitu subscriber pulih, ia melanjutkan pemrosesan tanpa publisher mengalami error 500.
  3. Future-Proofing (Evolusi Day-2 Tanpa Merombak Produsen):
    Jika arsitektur dimulai dengan pola Topic $\rightarrow$ Single Subscriber (seperti SNS $\rightarrow$ 1 SQS), ketika bisnis membutuhkan subscriber ke-2 (misal audit log atau fraud detection), tim infrastruktur cukup mendaftarkan subscription baru ke topic tersebut. Tidak ada 1 baris kode pun yang perlu diubah pada aplikasi produsen!

3. Perbandingan Strategis: Fan-Out vs Single Subscriber

Karakteristik Fan-Out Architecture Single Subscriber Queue
Rasio Pengiriman 1 ke N (Broadcast / One-to-Many) 1 ke 1 (Point-to-Point / Single Consumer)
Teknologi Cloud Umum GCP Cloud Pub/Sub, AWS SNS + Multiple SQS AWS SQS langsung, GCP Pub/Sub 1 Subscription, RabbitMQ
Tujuan Utama Dekopling multi-domain bisnis, paralelisme fungsi Buffering, rate limiting, perlindungan database hilir
Dampak Kegagalan Konsumen Terisolasi penuh; jika 1 subscriber gagal, subscriber lain tidak terganggu Pesan menumpuk di antrean hingga worker pulih
Biaya & Kompleksitas Sedikit lebih tinggi (biaya delivery dikalikan jumlah subscriber) Paling minimal dan efisien untuk workflow tunggal
